# Evolving AI backend reliability review

Reviewed September 22, 2026. This review covers the static web app in `docs/index.html`, its iPhone wrapper, and the Google Apps Script template in `docs/sheet-backend.gs`. The backend was deployed as version 13 of the existing `/exec` web app. The website was deployed from commit `36889d1`; the later iPhone source commit `7064c22` left `docs/` unchanged. The iPhone build has not been signed or distributed.

## What worked live

An authenticated synthetic attendee could read `counts`, `topic:T1`, and `posts` for `topic:T1` through the deployed Apps Script endpoint. The topic response included the synthetic attendee's existing question; the thread correctly contained zero posts. Earlier iPhone Simulator work confirmed that a synthetic submission reached the shared Sheet and that “Load my reading” restored it. After version 13 went live, the Benchmark browser confirmed a save by reading it back from the Sheet and loaded the synthetic question in the discussion. These checks establish a working path for that account at that time, not general availability. No live discussion post, debrief, or account change was made during the reliability rollout.

## Failure map

| Feature | Trigger and observed/likely result | Local protection added | Remaining limit |
|---|---|---|---|
| Save and reading progress | An opaque `no-cors` POST may fail or time out. A previous row can still be read, so existence alone gives a false success. | The app already requires an exact read-back match. New backend returns a row revision, and updated app sends it on later saves. A stale device now gets a conflict instead of overwriting newer work; the local draft remains. | The app cannot read the POST response. A failed confirmation can still be ambiguous if the subsequent GET fails. Older deployed clients that do not send revisions can still overwrite. Conflict resolution is manual. |
| Save to Sheet | A malformed submission, extra/duplicate topic choice, overlong answer, or payload above a Sheet cell limit can fail at write time. | Backend validates fields and ranks, caps encoded payload at 48,000 characters, and returns bounded errors. UI preserves the local draft and explains common cases. | Real Sheet parsing and size boundaries need a staging deployment test. |
| Concurrent save | Two devices load the same row; the older one saves later and erases the newer answer. A reload could accidentally pair an older draft with the newest revision. | Revision check runs under the script write lock. The app persists the revision with its local draft and refuses a stale revision after reload. First writes carry an absence marker to prevent a create race. | Requires deploying the backend before the updated web/iPhone client. Old clients still bypass the check for compatibility. Conflict resolution is manual. |
| Login / Load my reading | Wrong personal code, temporary lock, damaged stored key, and damaged payload previously had overlapping or misleading symptoms. A blank/damaged key could allow another code to claim the row. | Backend now distinguishes `bad_pin`, `locked`, `key_reset`, and `corrupt_payload`; a blank/damaged key cannot be replaced through normal submission. UI gives recovery wording without claiming the user can repair it alone. | There is no automated, identity-verified recovery flow. An organizer must handle a genuinely damaged key. The personal code is a guessable favorite-model answer, and email ownership is not verified. |
| Discussion load | A malformed post timestamp could make all posts in a thread fail to render. Invalid thread/topic requests and stale asynchronous responses could show the wrong page. | Invalid timestamps become blank, thread/topic values are validated, and the web app ignores responses for a page the user already left. | A Sheet outage, quotas, or slow scans still make discussion unavailable. All attendees with credentials can see every topic discussion. |
| Discussion post | A response/confirmation timeout may invite a retry that creates a duplicate. Text beyond 4,000 characters was silently truncated, then failed the app's exact confirmation. | Client-generated post IDs are persisted per pending post, including across threads; backend appends once per ID and checks exact ID on read-back. Oversized posts are rejected clearly. | Existing deployed backend ignores IDs until updated. No live discussion write was sent because it would appear to other attendees. |
| Sheet integrity | Attendee text beginning with `=` can be interpreted as a spreadsheet formula; malformed callback names can produce executable JSONP output. | Display text is escaped as literal Sheet values; callback identifiers are validated. Local tests cover formula text in submissions, posts, and debriefs. | Apps Script/Google Sheets behavior should be verified against a staging Sheet. JSONP remains an unsuitable long-term transport for sensitive data. |
| Backend availability | Write-lock wait failure, Sheet outage, or Apps Script exception can return an opaque failure or raw internal error. | Lock acquisition is now caught; handlers return `backend_error` and log server details. Invitation-code check no longer needs Sheet access. | The local draft cannot be saved in the Sheet while the service is unavailable. Apps Script execution quotas and full-tab scans remain capacity limits. |
| Invitation check | The browser can proceed when the gate lookup fails; the subsequent save may reject. Repeated incorrect checks could lock the gate check. | The backend still enforces the invitation code on a new submission and now reports invalid while the gate check is locked. | The frontend deliberately allows offline drafting, so initial validation may look successful before the backend is reachable. |

## Verification

`node --test tests/*.test.cjs`: 63 passed, 0 failed after the follow-up review. A generic iOS Simulator build of the `Evolving AI` scheme succeeded with code signing disabled. Its bundled `index.html`, `docs/index.html`, GitHub Pages, and the Benchmark URL all had SHA-256 `12058c0e300ebae4aac888096060601e811d8b7ecbc0d932fe1d0657f1188076`. GitHub Pages run 70 completed successfully. A production read of the existing synthetic attendee returned a row revision. In the live Benchmark browser, Save my progress reported confirmation from the organizers' Sheet, and a topic discussion loaded the synthetic test question. The new failure-path tests use a synthetic in-memory Apps Script/Sheet harness; they do not prove every Google production behavior. `git diff --check` passed. No load test or live discussion write was run.

## Architecture work still needed

For durable authentication and privacy, replace the favorite-model secret and JSONP GETs with verified attendee identities or individual random invitation credentials behind a small authenticated API. The current JSONP requests put codes in URLs and can return attendee responses; Google recommends JSONP only for non-sensitive data ([Apps Script Content Service](https://developers.google.com/apps-script/guides/content)). Add an organizer-assisted recovery flow, a visible conflict reconciliation path, and monitoring/backups. Apps Script quotas and concurrent execution limits remain relevant ([Apps Script quotas](https://developers.google.com/apps-script/guides/services/quotas)). Google documents that `Range.setValues` interprets leading `=` as a formula ([Range.setValues](https://developers.google.com/apps-script/reference/spreadsheet/range#setvaluesvalues)); production Sheet verification of the literal-text fix is a release check.
